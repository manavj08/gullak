# Changelog

## V2.5 — CSV Export + Real Password-Reset Email

**Two independent utility features, both additive:**

- **Transaction CSV export**: new `GET /api/wallet/transactions/export/`, streaming a CSV with columns `Date, Type, Category, Amount, Account, Description`. Honors the same query params as the transaction list (`type`, `account`, `category`, `settled`, `include_gullak`), scoped to the requesting user only, Gullak legs excluded by default. "Export CSV" button added to the Transactions page, passing through whatever type filter is currently active. Also fixed a pre-existing bug in that file: the empty-state "Add transaction" button called `navigate(...)` without the hook ever being imported.
- **Real password-reset email**: `POST /api/auth/password/reset/` no longer returns the reset `uid`/`token` in the API response — it now sends an actual email with a tokenized link to the frontend's `/reset-password` page, via a new `accounts_app/services.py`. Which backend sends it is decided by environment variables: SMTP if `EMAIL_HOST_USER`/`EMAIL_HOST_PASSWORD` are set, otherwise Django's console backend (prints to the server log) — so local dev keeps working with zero config, while production just needs env vars set. New settings: `EMAIL_HOST(_USER/_PASSWORD)`, `EMAIL_PORT`, `EMAIL_USE_TLS`/`_SSL`, `DEFAULT_FROM_EMAIL`, `FRONTEND_URL` (used to build the reset link), `PASSWORD_RESET_TIMEOUT` (default 1 hour, read natively by Django's token generator). HTML + plain-text templates live in `accounts_app/templates/accounts_app/emails/` — caught and fixed a subtle bug while testing: Django's template engine HTML-escapes `&` even in `.txt` templates by default, which was mangling the `&token=` part of the link; fixed with `{% autoescape off %}`.
- **Security posture unchanged, made explicit in tests**: the response is identical whether or not the email exists, and identical whether or not the send actually succeeded (failures are logged, not surfaced) — the endpoint still can't be used to enumerate accounts or probe for mail-server outages. Tokens remain single-use (Django's generator bakes the current password hash into what it checks, so it's invalidated the moment the password changes).
- **Frontend**: `ForgotPasswordPage.jsx` updated to drop the now-defunct dev-link shortcut (there's no token in the response to build one from anymore) in favor of a "check your inbox" message.

**Testing**: backend suite grew from 250 to **259 tests** — 9 new for CSV export (header/column shape, filtering, Gullak-leg exclusion, cross-user isolation, auth), and the existing 2-test `PasswordResetTests` class was rewritten and expanded to 8 (parses the real emailed link instead of reading a token off the response; adds single-use-token, invalid-token, malformed-uid, identical-response, and simulated-SMTP-failure cases). Also fixed a test-isolation issue these expanded tests exposed: `PasswordResetTests` now clears the shared throttle cache in `setUp`/`tearDown`, since it was exhausting the `auth` scope's 10/min budget and intermittently breaking `RegistrationLoginTests` (alphabetical test-class ordering ran it first). `python manage.py check`, the full 259-test suite, `npx oxlint`, and a production frontend build all pass.

## V2.4 — Dashboard Analytics: Net Worth Over Time & Spend by Category

**Two new read-only aggregation endpoints in the existing `wallet` app (no new Django app, no changes to Accounts/Transactions CRUD/Block-Unblock/Goals/Split logic):**

- **`GET /api/wallet/analytics/net-worth-history/?days=30`** → `[{"date", "net_worth"}, ...]`, oldest first. Daily Transaction / Savings / Gullak balances are reconstructed *exactly*: today's net worth, with each day's income/expense/lend/borrow transactions reversed back off it (transfers and Gullak block/unblock move money between the user's own accounts, so they net to zero in the total and don't need reversing). Revenue Generation and Loan/Debt accounts have no dated transaction ledger in this app — their *current* value is held constant across every day in the range, documented as an explicit, deliberate approximation rather than a silent assumption.
- **`GET /api/wallet/analytics/spend-by-category/?days=30`** → `[{"category", "amount"}, ...]`, largest first, `EXPENSE`-type only, using the app's actual `TransactionCategory` choices (Food/Transport/Bills/Shopping/Other/Uncategorized) rather than adding new categories not present in the model.
- **Demo data improvement**: `seed_demo_data.py` now backdates its transaction timestamps via a `QuerySet.update()` call after creation (bypasses `auto_now_add` without touching the `Transaction` model or the real create-transaction flow), so both charts show a realistic multi-day shape immediately after seeding instead of one flat day.
- **Frontend**: `NetWorthChart.jsx` (area chart, 30d/90d/1y range toggle, trend indicator) and `SpendByCategoryChart.jsx` (horizontal bar chart), added as one new section on `HomePage.jsx` — the existing dashboard layout and every other section were left untouched. Added `recharts` (v3), then lazy-loaded both components via `React.lazy`/`Suspense` after an initial build flagged a 785KB main bundle — recharts now ships as its own ~330KB chunk, main bundle back to 405KB.

**Testing**: backend suite grew from 244 to **250 tests** — 19 new, covering reconstruction correctness (including a full sweep: expense/income today, a backdated expense only affecting dates before it, transfer-neutrality, Revenue Generation/Loan-Debt held constant), category aggregation (ordering, omission of zero-spend categories, income/lend correctly excluded, day-window boundaries), and the two API endpoints (day-param clamping/validation, auth, cross-user isolation). `python manage.py check`, the full suite, `npx oxlint`, and a production frontend build all pass; the seed command was run fresh and its output spot-checked against both new service functions directly in a shell.

## V2.3.1 — Settlement Mathematics Module (`splits/services/settlement.py`)

**Refactor + new capability, additive — no breaking changes to any existing endpoint, response shape, or test:**

- **`splits/services.py` split into a package** organized by responsibility, so settlement math has one clean, independently-testable home:
  - `services/settlement.py` — **the single source of truth for every money computation in `splits`**: split-type share rounding (`equal_shares`, `custom_shares`, `percentage_shares`), pairwise debt netting (`net_pairwise_debts`), global debt simplification (`simplify_global_debts`), settlement generation/lifecycle (`generate_settlements`, `mark_settlement_paid`), and the "Show Calculation" explainability trail (`explain_expense`, `explain_group`, `explain_settlement`).
  - `services/groups.py` — group membership management (unchanged logic, moved as-is).
  - `services/expenses.py` — expense creation/deletion; delegates all share-amount math to `settlement.py` rather than computing it itself.
  - `services/upi.py` — UPI id validation/save and payment-info generation (unchanged logic, moved as-is).
  - `services/__init__.py` re-exports every function, so `from . import services; services.create_group(...)` keeps working unchanged everywhere (views, permissions, existing tests) — **zero call-site changes required**.
- **Pairwise netting made a pure, reusable function**: `net_pairwise_debts(debts)` takes plain `(debtor_id, creditor_id, amount)` tuples and cancels mutual debts down to a single net direction + amount per pair (*A owes B ₹500, B owes A ₹200* → *A owes B ₹300*) — no database involved, so it's directly unit-testable and reusable outside a Django request.
- **Global simplification made a pure, reusable function**: `simplify_global_debts(net_balances)` takes a plain `{user_id: Decimal}` dict and returns the minimal set of payer→payee transfers via the standard greedy largest-debtor-vs-largest-creditor match.
- **One documented, consistent rounding rule**, stated once at the top of `settlement.py` and used by every share-splitting function: floor each share to whole paise, then hand out the leftover paise one at a time, in ascending user-id order. Explicitly tested against the required ₹100/3, ₹100/6, ₹10/3, and ₹0.01/3 cases, plus a sweep across a wider range of awkward amounts/participant counts confirming shares always sum exactly to the total.
- **New: "Show Calculation" API endpoint** — `GET /api/splits/groups/<id>/settlements/<settlement_id>/calculation/` (members only), backed by `explain_settlement()`. For a `pairwise` settlement it returns exactly the expenses that produced it, each broken down as *description, amount, who paid, every participant's share, and who owes the payer as a result* (matching the project's required format, e.g. *Dinner ₹900 → Manav paid ₹900 → Rahul owes Manav ₹300, Amit owes Manav ₹300*). For a `global` settlement — where a simplified amount can route a debt through a third person and so can't always be traced to one expense between two specific people — it instead returns the full group expense ledger plus each person's overall paid/share/net.

**Testing**: backend suite grew from 179 to **225 tests** — 46 new tests in `splits/test_settlement.py`, split between fast pure-function tests (no database) for the rounding rule, pairwise netting, and global simplification, and integration tests that exercise the same math through real groups/expenses/settlements. Explicitly covers: equal/custom/percentage split math, pairwise settlement, global settlement, multiple expenses, mutual debts, zero balances, uneven divisions, decimal rounding (all four required cases), multiple group members (4-person group), already-paid settlements correctly reducing future balances in both settlement modes, and the Show Calculation explainability trail at both the expense and settlement level. `python manage.py check` and the full 225-test suite (all pre-existing tests included, unmodified) pass.

## V2.3 — Standalone Split Groups (`splits` app)

**New capability, additive — no breaking changes to existing schema, apps, or flows:**

- **New `splits` Django app**: `SplitGroup`, `SplitGroupMember`, `SplitExpense`, `SplitExpenseShare`, and `Settlement` models, mounted at `/api/splits/`. Deliberately **standalone** — unlike the `expenses` app's group-expense feature, a `SplitGroup` is not tied to a `wallet.Account` or the `social` app's invite/admin-transfer flow. Any user can create a group directly with any other user IDs, Splitwise-style.
- **Two split-type additions beyond `expenses`**: alongside equal and custom-exact splits, `splits` adds **percentage splits** (per-person percentages that must sum to 100; converted to Decimal shares with the same one-paisa-at-a-time remainder distribution used elsewhere).
- **Settlement modes, set per group**: `GLOBAL` (greedy debt-simplification across the whole group — same algorithm as `expenses`) or `PAIRWISE` (direct net balance kept between every pair of members, with no cross-pair simplification). `POST .../settlements/recalculate/` regenerates pending settlements from current balances; already-`PAID` settlements are kept as history and factored into balances, not recalculated away.
- **Membership rules**: any current member can add a new member; the group creator can remove anyone, any other member can remove only themselves (leave); the creator cannot be removed.
- **UPI/QR**: reuses the existing `User.upi_id` field (added in V2.2) rather than a new one. `POST /api/splits/upi/save/` validates and saves it; `GET .../settlements/<id>/payment-info/` returns the payee's UPI ID/name/amount/note plus a ready `upi://pay?...` deep link (frontend renders the QR — no image generated server-side, no new dependency added).
- **Permissions**: all group-scoped endpoints are members-only, returning `404` (not `403`) for non-members — matching the existing `social`/`expenses` convention of not leaking group existence to outsiders. Only the payer or whoever logged an expense can delete it; only the payee can mark a settlement paid.
- **No changes to any existing app**: `wallet`, `social`, `expenses`, `goals`, `streaks`, and `accounts_app` are untouched — `splits` only adds itself to `INSTALLED_APPS` and one `include()` in `config/urls.py`.
- **Small additive API surface added while building the frontend below** (none of these change or break the endpoints above): `pending_settlement_total` on `GET /api/splits/groups/` (correlated-subquery aggregate, avoids the classic multi-join fan-out bug), `PATCH /api/splits/groups/<id>/` to change settlement mode after creation (creator only), and `GET /api/splits/users/lookup/?username=` to resolve a username to a user id before adding them (the existing `accounts_app` lookup deliberately omits the id, since that flow requires the invitee to accept — `splits` adds members directly with no acceptance step, so the id has to be exposed here). Also fixed `SplitExpenseSerializer.paid_by`/`created_by` to return nested `{id, username}` objects instead of bare ids, matching the `expenses` app's existing convention (caught before shipping, via the frontend that consumes it).
- **New frontend**: complete `splits` UI at `frontend/src/features/splits/` — six screens (Split Groups, Create Group, Group Detail, Add Expense, Settlement, Split Settings), added to both the desktop side rail and mobile bottom nav. Split-type and settlement-mode choices use a new `Radio` component added to the shared `ui.jsx` kit. QR codes are generated client-side with the `qrcode` package (dynamically imported — not in the initial bundle). "Show Calculation" on the Settlement screen is computed entirely client-side from already-loaded expense data (no extra API call): for `pairwise` groups it lists the specific contributing expenses; for `global` groups it shows each person's overall paid-vs-owed net, since a simplified group-wide settlement can't always be traced to one expense between two specific people. `AddExpense` mirrors the backend's rounding-remainder math client-side for a live per-person preview before submit — the backend still recomputes and validates everything with `Decimal`.

**Testing**: backend suite grew from 143 to **179 tests** — 36 new tests in `splits/tests.py` (32 for the core app, 4 for the small additions above) covering equal/custom/percentage split math (incl. rounding), membership add/remove rules, GLOBAL vs. PAIRWISE settlement generation and balance conservation, recalculation clearing stale pending settlements while preserving paid history, payee-only paid confirmation, UPI ID validation, API-level members-only 404 gating, the pending-settlement-total annotation, creator-only settlement-mode changes, and the username-lookup endpoint. `python manage.py check`, the full backend suite, and a production frontend build (`npm run build`) all pass. `npx oxlint` on every new/changed frontend file: 0 warnings, 0 errors.

## V2.2 — Group Expense Split & UPI Settlement

**New capability, additive — no breaking changes to existing schema or flows:**

- **New `expenses` Django app**: `ExpenseEntry`, `ExpenseShare`, and `Settlement` models, available only on Family & Friends **group** accounts (`owner_type == shared_group`) via a new "Group expenses & settlements" button on the shared-account detail page. Relationship/pair accounts don't get this feature — expense-splitting assumes 3+ people is the common case, and pair accounts already have their own simple contribute/unblock flow.
- **Separate debt ledger by design**: logging an expense never touches the group account's pooled `block_balance` or any member's `SharedContribution.contributed_amount`. It's purely a "who owes whom" ledger, independent of the existing pooled-savings feature — this avoids any interaction with the emergency-unblock caps, visibility rules, or contribution tracking already built for shared accounts.
- **Two split types**: split equally (remainder paise distributed one cent at a time in a deterministic order, so shares always sum exactly to the total) or exact custom amounts per participant (rejected server-side if they don't sum to the total).
- **Settlement generation**: `expenses.services.generate_settlements()` recomputes each member's net balance from all logged expenses (offset by any already-`PAID` settlements) and produces the minimum number of payer→payee transfers using a greedy debt-simplification algorithm. Regenerating replaces the previous `PENDING` set; `PAID` settlements are kept as permanent history and excluded from the recalculation.
- **UPI settlement**: new nullable `upi_id` field on `User` (self-reported, unvalidated — same "no payment gateway" philosophy as the rest of the app), used to build a `upi://pay?pa=...&am=...` deep-link on each pending settlement. The person who owes money taps "Pay via UPI" to open their own UPI app pre-filled; the person who was owed money manually confirms via "Confirm received" once they've actually gotten paid. No real money moves through the app at any point.
- **Permissions**: only current group members can view/log expenses (non-members get 404, matching the existing `social` app's not-403 convention); only the payer or whoever logged an expense can delete it; only the payee can mark a settlement paid.
- **New frontend pages**: `GroupExpensesPage` (`/shared-accounts/:id/expenses` — list + log-expense form) and `SettlementsPage` (`/shared-accounts/:id/settlements` — pending/paid lists, UPI pay button, confirm-received). Profile page gained a UPI ID field.

**Testing**: backend suite grew from 123 to **143 tests** — 20 new tests in `expenses/tests.py` covering equal/exact split math (including the rounding-remainder edge case and mismatched-total rejection), membership/permission gating, settlement generation's balance-conservation property, regeneration replacing pending settlements while preserving paid history, payee-only paid confirmation, UPI link presence/absence, and `shared_pair` accounts being correctly rejected. Zero existing tests were modified.

**Not affected**: the core V1 ledger, block/unblock math, streaks, shared-account contributions/visibility/emergency-unblock, goals, split suggestion, and notifications — all pass unchanged. `makemigrations --check --dry-run` confirms no missed model changes.

- `GoalSerializer` now exposes `funding_source`, `is_common_goal`, and `funding_shared_account_id`; creating a goal with a `funding_shared_account_id` now checks the requester is actually a member of that shared account, and `funding_shared_account_id` can never be changed via update once a goal is created (it's load-bearing for the contribution history already tracked against it).

- `GoalsPage`'s goal cards show a "Shared →" badge/link for any common goal, linking to the same shared-goal detail page.

## V2 — Shared & group accounts, notifications, smart split, public landing page

**Major new capability (backend + frontend), additive to V1 — no breaking schema changes:**

- **Shared (Relationship) accounts**: a simple 2-person pooled account, no admin. Either member can invite the other by username, contribute from their own accounts, or emergency-unblock their own contributed share.
- **Family & Friends group accounts**: 2+ members, with an admin (creator by default). Admin can invite, remove members, and initiate an admin-role transfer — the target member must explicitly accept before the transfer takes effect (never a unilateral handoff). An admin can't leave without transferring the role first.
- **Username-based invites**: looked up by username (not phone/email), and must be explicitly accepted before membership is granted — a `GroupInvite` record tracks pending/accepted/declined status.
- **Aggregate-only visibility, enforced server-side**: `social.services.get_visible_contributions()` is the *only* way contribution data is ever serialized for a shared account — a member's own contribution is returned in full, every other member's is folded into one combined `others_aggregate` figure. There is no code path that returns a per-member breakdown to the client.
- **Own-share-only emergency unblock**: a new `SharedContribution` model tracks each member's running net contribution into a shared account's pool, and `wallet.services.emergency_unblock_own_share()` caps any unblock at that member's own figure — never the pool total, never another member's share, and with no consent step needed since it's the member's own money.
- **No cross-funding**: `Goal` gained a nullable `funding_shared_account_id` — a goal is funded from personal Gullak (default) or one specific shared account, never both. `goals.services.add_funds_to_goal()` now branches on this and caps against the correct pool.
- **Smart Gullak-split suggestion**: `goals.services.compute_urgency_split()` implements `urgency_score = (target_amount - allocated_amount) / days_until_deadline` and returns a proportional split of a new amount across underfunded, non-achieved personal goals with a deadline. Advisory only — nothing is applied until the user reviews/overrides and confirms via `POST /social/split-suggestion/apply/`.
- **Behavior change, confirmed in scope discussion**: emergency-unblock overage that eats into goal-allocated funds is now deducted **automatically and proportionally** across underfunded personal goals, instead of leaving a `PendingGoalDeduction` for the user to manually resolve on their next Home visit. The record is still created, but pre-resolved (informational, for history), and an in-app `Notification` explains exactly what was adjusted. **The old manual-resolution service function was kept, not deleted** — it's simply no longer called by the live flow, and remains fully tested in case it's needed again.
- **Notification Center**: a new `Notification` model covers invites, admin-transfer requests, member-joined/left, admin-changed, and goal-deduction notices. Actionable notifications (invite, admin transfer) stay visibly pending after being viewed — viewing only ever moves `unread → read`, never to `actioned`; only actually accepting/declining moves it to `actioned`. The nav shows an unread-count badge, refreshed on navigation (not real-time/polling, by deliberate simplicity choice).
- **Public landing page** at `/`: explains the app's features with Login/Register CTAs. An already-authenticated visitor is redirected straight to `/unlock` (if they have an MPIN) or `/home` — they never see the marketing page.
- **New `social` Django app**: `SharedAccountMember`, `GroupInvite`, `GroupOccasion`, `AdminTransferRequest`, `Notification`, `SharedContribution` — kept separate from `wallet` since membership/invite/visibility/admin logic is a distinct concern, and V1 had already reserved `Account.owner_type` for this expansion.
- **`Account.owner_type`** extended from `individual | shared` (the V1 placeholder, unused) to `individual | shared_pair | shared_group`.
- **Username** is now used for the invite-lookup flow (`GET /api/auth/username-lookup/`); it was already unique on the `User` model via Django's default `AbstractUser`, so no data migration was needed.

**New frontend pages**: `LandingPage` (public `/`), `NotificationsPage`, `SharedAccountsPage`, `CreateSharedAccountPage`, `SharedAccountDetailPage`, `SplitSuggestionPage`. Nav (side rail + bottom nav) gained Shared-accounts and Notifications entries, the latter with an unread badge.

**Testing**: backend suite grew from 56 to **102 tests** (all passing) — 43 new tests in `social/tests.py` covering invite flow, membership/admin rules, the visibility rule, own-share-unblock, no-cross-funding, the split-suggestion formula, and the notification lifecycle; the two V1 tests asserting the old manual-only emergency-unblock behavior were rewritten (not deleted) to assert the new automatic behavior, and the legacy manual-resolution function got its own dedicated test class so it stays verified even though it's no longer on the live path.

**Migrations**: two small additive migrations (`wallet.owner_type` choice extension, `goals.funding_shared_account_id`) plus one new-app initial migration (`social`) — all additive, no existing V1 migration was altered, and a V1 database can be migrated forward with a plain `python manage.py migrate`.

**Postman collection** renamed to `Gullak_API_V2.postman_collection.json`, with 5 new folders: Shared & Group Accounts, Invites & Admin Transfers, Notifications, Smart Split Suggestion, and Username Lookup.

**Demo data**: `seed_demo_data` now creates a second demo user (`demo2@gullak.app` / username `demo_friend`) and sets up a complete shared-group-account flow between the two demo users (invite sent and accepted, contributions from both sides, a common goal funded from the shared pool) — the V2 features are visible immediately after seeding, no manual setup needed.

**Not affected:** the core V1 ledger (accounts, transactions, block/unblock math), streaks, and personal-goal funding for goals that don't opt into shared funding — those are unchanged apart from the new optional `funding_shared_account_id` field, which defaults to null (personal Gullak).

## Previous — Gullak as a real account, Decimal rupees, goal add-funds, overage resolution

**Major architecture change (backend + frontend):**

- **Money storage migrated from integer paise to exact `Decimal` rupees.** Every money field on every model (`Account`, `Transaction`, `Goal`, `PendingGoalDeduction`) is now a `DecimalField(max_digits=12, decimal_places=2)`. The API accepts and returns decimal strings (e.g. `"150.50"`) directly — no unit conversion anywhere in the frontend. This required new migrations; a fresh `db.sqlite3` was generated as part of this change (existing local databases from earlier versions are not compatible and should be recreated via `python manage.py migrate` on a clean database).
- **Gullak is now a real `Account`** (category `gullak`), not a computed total. Exactly one is auto-created per user via a `post_save` signal the moment their account exists (including via `createsuperuser`), enforced as a database-level unique constraint. It cannot be created manually (rejected at the serializer level) or deleted.
- **Blocking funds now moves money into the Gullak account directly**, recorded as two linked `Transaction` rows (`gullak_block` on the source account, `gullak_block` on Gullak). These "Gullak legs" are excluded from the general Transactions list by default — they only appear on the Gullak account's own detail page (`?include_gullak=true` reveals them, used internally by that page).
- **Goals**: the old "adjust allocation" (set-to-any-value) action is gone. The only way to increase a goal's funding through the UI now is **Add funds** (`POST /goals/{id}/add-funds/`), which only ever increments — still capped so the sum across all goals can never exceed the live Gullak total.
- **Emergency-unblock overage handling**: unblocking money that's still within your *unallocated* Gullak funds behaves exactly as before — no side effects. But if the amount unblocked eats into money already committed to a goal, nothing is silently reassigned. Instead a `PendingGoalDeduction` record is created, and the next time the user opens Home, a modal blocks further interaction until they choose which goal (or split across several) the overage should come from.
- **New Accounts page layout**: users can toggle between a responsive Grid view and a horizontally-scrollable view; the choice is remembered locally per device. Gullak is pinned as its own prominent card above the category groups.
- **New Transactions history page** (`/transactions`, reachable via Home → "View all"): full list with type filter chips, separate from the "Add transaction" form.
